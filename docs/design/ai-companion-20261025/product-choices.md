## 推荐和可选择范围

**建议 C：日常打开一个连续主入口，同时保留历史、会话内搜索、清楚的话题边界和“新话题”。此建议尚待 LI 选择。**

推荐的第一步把“连续”限定为入口和阅读体验：返回时继续上次可用、结果已确定的会话，
主动消息可以提示用户进入其对应话题；底层既有会话不合并、不复制、不改保留期。
历史入口常驻可见。先支持“选一段历史 → 在这段会话中查找”；跨会话全文检索是待定扩展，
不可用一个搜索框暗示已经具备。新话题仍是明确动作，不自动把上一话题加入新请求。

这个范围让日常返回少一次选择，又给混话题、纠错、隐私和维护留下已有边界。
主动消息回复归属、未读状态和来源卡片仍需要 Integration 收口新合同。

| 选择 | 用户看见什么 | 优点 | 主要代价与需要明确的边界 |
| --- | --- | --- | --- |
| A：多对话 + 主动入口 | 会话列表与新建入口保留；独立“主动联系”入口或卡片 | 兼容当前行为最多；不同事项隔离清楚；整段删除好解释 | 每次返回更容易先做会话选择；主动入口与聊天之间多一步；不能产生两个未读计数来源 |
| B：单一连续时间线 | 一个长时间线；主要新建/列表入口退居管理位置 | 首次和日常返回最直接；主动消息自然插入同一流 | 混话题和旧上下文干扰明显；整段删除影响范围更大；若真的合并存储，将触及 90 天保留锚点和迁移，成本最高 |
| C：连续主入口 + 历史/话题 | 直接回到可续聊位置；历史、查找和新话题始终可找到 | 返回顺畅，同时保留找回、隔离和删除的能力；可分阶段演进 | 必须解释“主入口”不等于永久记忆；话题标签不能伪装成已有服务端标题；需要一致的主动消息归属与恢复位置 |

## 逐项比较

| 用户流程 | A | B | C（推荐候选，未确认） |
| --- | --- | --- | --- |
| 首次使用 | 先说明 AI 数据使用，随后空会话；“新建”不应成为使用门槛 | 数据使用后就是时间线；最少导航 | 数据使用后直接空主入口；“先聊聊”与“先了解数据使用”均可见 |
| 日常返回 | 列表定位最近会话；保留未发草稿 | 同一时间线回到上次阅读点 | 回到当前可用话题和阅读点；未知操作优先恢复；不凭“最近时间”跨账号恢复 |
| 主动消息进入 | 主动入口显示未读，点击携带受信消息/会话定位 | 消息进入流，按时间出现；必须避免被长历史淹没 | 主入口出现未读卡片，打开原消息并保留归属话题；无须伪造用户提问 |
| 原因、来源、回复 | 入口 → 消息 → 原因/来源 → 同话题回复 | 流中展开原因；回复对象需要显式标示 | 消息旁“为什么收到”及“本次参考”；输入框上方标示回复哪条消息、哪个话题 |
| 多话题混杂 | 独立会话隔离较强；可显式切换 | 单流最易被旧话题污染；需另增上下文截断/分段语义 | 新话题沿用会话边界；可查旧话题，但查阅不自动附加给模型 |
| 用户纠正 | 纠正留在当前会话；请求中的最新用户话语优先 | 需防止远处旧答复再次被选中 | 当前纠正与“本次排除”可见；旧 AI 建议不变成用户事实；不擅自创建永久偏好 |
| 历史查找 | 现有列表 → 当前会话内搜索 | 需给隐藏的管理入口保留可发现性；加载范围仍需说明 | 明确“当前话题内已加载消息”；切换历史另行确认草稿；跨话题搜索待合同 |
| 删除与隐私 | 删除整段会话，范围清楚 | 单流整体删除可能过大；单条/按日期删除尚无批准 | 删除当前会话，确认展示范围；“新话题”不等于删除；不新增单条删除或撤销承诺 |
| 迁移和保留 | 最少改动；新增主动消息仍需合同 | 真正合并会话风险最高；持续写入可能改变旧内容实际保留时间 | 既有数据原样可读；先保留会话容器与 90 天锚点，不迁移内容 |
| 实现和维护 | 导航低成本，主动投递是共同的新成本 | UI 看似简单，数据生命周期和恢复最复杂 | UI 中等成本，能复用现有读取/删除/未知结果；不能把“话题”另造一套未批准实体 |

以上是基于当前结构的相对判断，不是工期、价格或用户研究测量。

## 第一条可评审纵向流程（所有方案共用）

1. 用户显式要求对一件事稍后跟进，并确认时间、时区与允许的投递方式。
2. 到期前重核当前账号/用途同意/来源有效性/频率/安静时段。
3. 保存真正的主动 assistant 消息及待批准的最小来源/触发/归属元数据。
4. App 前台显示“有一条跟进”；打开该消息后显示原要求与时间，不把送达当已读。
5. 用户查看原因、查看当前仍有效的来源、回复；回到原归属会话。

这是推荐首批场景，不是已批准默认开启。另两类比较：Going 活动临近（需最新活动状态、
时区、撤回后失效；Interested 不触发 Going 提醒）；近期签到轻问（额外数据用途与显式类别
许可；不得诊断心情、暗示欠回复）。两类暂不作为第一条纵向流程的必需前置。

系统推送、后台、应用终止后的送达均由 Proactive 的实际平台/服务方案证明。
HTML 演示只模拟 App 内页面，不证明这些能力。未读/已读、静音与关停、过期/撤回后处理、
设备离线及重复触发均不能由前端计时器或模型自由文本决定。
