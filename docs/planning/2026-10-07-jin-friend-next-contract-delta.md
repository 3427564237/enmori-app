## One recommended increment

Recommend an authenticated, read-only **My Friends list**, displaying the current authorized Username and DisplayName of already accepted friends, one bounded page at a time. It advances part of `friends-page` without needing Event participation, recommendation inputs or Activity sources. It is not completion of that route: approved name-based Search My Friends and the remaining actions still need their own scoped delivery. Do not substitute exact Add Friend search or a filter over one loaded page for that search.

Recommend first validating this new read in the explicitly isolated Emulator/Android environment, after its specific approval. An alternative is to wait for real-account contracts and implement the same read against those sources. The isolated option produces narrower evidence sooner; it cannot establish real-user readiness. Neither option is selected by this document.

The [42-route/38-state target and five owner/reviewer pairs](../decisions/2026-09-24-sprint3-figma-coverage-ownership.md) remain unchanged. No new architecture, dependency, general pagination framework, recommendation formula or request lifecycle redesign is proposed.

## Candidate contract delta for F04/F05

Everything in this section is proposed, including numeric bounds and storage names. Existing lookup/send/inbox/accept/decline contracts, canonicalization, recipient authorization, 30-day expiry, first-valid-commit races and terminal no-history semantics stay intact.

**Operation and fields.** Propose `GET /v1/me/friends?cursor=...`, verified requester only, no caller-selected AccountId, search term or page size. Return `200 {friends:[{username,displayName}],nextCursor:string|null}`. No relationship IDs, request references, timestamps, counts, visibility values, reasons, ranking data or full Profile. These fields are for this screen only: no recommendation, Activity, AI or shared Home consumer is authorized. SHI/DU producer reads and provider access are unnecessary for this increment.

**Owner index.** Propose `friend_lists/{accountId}` with `{initialized:true}` only for the explicitly seeded isolated population; absence/invalid state fails closed. Children `members/{entryRef}` contain only `{pairKey}`. Each entry reference is a fresh random UUID, distinct for the two owners and independent of AccountId, Username, pair key and request reference. The existing pair gains internal `listRefs` mapping its two AccountIds to those references. The pair remains relationship/block authority; the index cannot grant access.

On the existing valid acceptance transition, atomically create both owner pointers and set the two references with `friendship=true` and pending consumption. Failure rolls back all effects; repeated/stale accept still has the existing unavailable behavior and creates no extra pointers. Existing accepted synthetic pairs require explicit complete fixture seeding before setting `initialized`; absence of an index must not manufacture an empty set. No real-account backfill, runtime repair, migration or new scheduler is proposed. These are narrow index-maintenance additions to acceptance, not a new request protocol.

Fixture block/temporary ineligibility keeps pointers but hides rows through fresh authority checks. Recommend removing both list pointers and their pair references in the existing permanent-deletion fixture transaction; this defines only synthetic index cleanup, not real Friendship deletion semantics. Index records have only a current-list purpose, contain no copied names/history and disappear with the isolated environment. Real lifecycle cleanup/retention and population completeness remain unapproved; retaining this index for real Accounts is blocked on those decisions.

**Read bound and cursor.** Use one read transaction: authorize owner, verify initialization, scan at most 20 owner pointers plus one lookahead in entry-reference order; validate/project only the first 20. For each, reread the authoritative pair, target eligibility, current Account presentation and matching canonical Username reservation. Validate owner membership, accepted state, pair-key consistency and `listRefs` correspondence. Known current privacy/eligibility denial omits the row; missing, malformed or unavailable authority is a page failure, not an authorized omission or success-empty result. No scan-to-fill loop, global Account scan or unbounded collection read.

Recommend base64url encoding of the last scanned random entry reference as the continuation, only when lookahead exists. It is not an encoded AccountId/pair key. Require canonical decoding to one UUID and validate its existence within the authenticated owner's index; a foreign-owner/invalid/stale cursor receives the same validation error. That extra lookup is bounded. A transaction attempt reads at most 21 index rows, four point reads for each of 20 candidates, and five owner/initialization/cursor documents: 106 documents at most; no target expansion for lookahead. Execution must verify that bound and the needed document-ID ordering in the actual Emulator.

Filtered pages may contain zero rows and a continuation. Do not return a total, hidden-row count or explanation, or claim that the visible page is the complete friendship set. Pages are fresh independent reads, not one frozen multi-page snapshot. Concurrent inserts before the cursor may require Reload; a removed cursor also requires Reload. No stored pagination session or read-time cleanup write is proposed.

**Errors and UI.** Propose reuse of existing auth/onboarding/forbidden errors, `REQUEST_INVALID` 400 for invalid inputs/cursors and `SERVICE_UNAVAILABLE` 503 for authority/storage failure, with existing generic envelopes; confirm these mappings before normative API changes. Failed reads clear candidate output rather than showing successful emptiness. Replace the visible page on Next, clear rows on Reload/account change, and discard late responses using the existing operation/auth guards; no new persistent cache. Proposed copy: `No friends available on this page.` when a page is empty, `Next page` only with continuation, `Reload` to restart. Availability copy makes no claim that the user has zero accepted friends. Returning from a newly accepted request and reopening/reloading the list performs a fresh read; no previously held lookup result grants list access.
