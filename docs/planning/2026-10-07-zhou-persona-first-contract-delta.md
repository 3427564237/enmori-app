## P01 candidate operations and values

All six routes require the existing verified Firebase Auth Principal and completed-account boundary. Resolve its UID through the existing Auth Binding to the internal Account ID on every transaction. No body/query/header supplies an owner identity; ordinary users and Admin have no cross-owner bypass. Persona management itself does not invoke optional AI processing, so recommend no new consent gate for these management operations; this does not authorize later AI use.

Candidate editable input `PersonaInput` has exactly `displayName`, `tone`, `responseLength`, `formatStyle`. Unknown fields are rejected. `displayName` is a well-formed Unicode string, normalized with ECMAScript `trim()`, then 1–50 Unicode scalar values; reject remaining `Cc`, `Cf`, `Zl` and `Zp` characters. Preserve internal spacing; no Unicode composition normalization or uniqueness requirement. Render as plain text. The limit/normalization are proposed choices, not inferred from Profile's existing rule.

The exact enums remain Q19: `tone=neutral|warm|encouraging`, `responseLength=concise|balanced|detailed`, `formatStyle=plain|bulleted`. No omitted/null editable field or caller-provided timestamp/revision value is accepted as a new value.

`PersonaView` contains exactly `personaId`, the four editable fields, `createdAt`, `updatedAt`, and `revision`. IDs are opaque 64-character lowercase hexadecimal strings generated as specified in P03; they convey neither ownership nor permission. Revisions are safe integers: owner `stateRevision` is 0 through 9007199254740991, live Persona `revision` is 1 through that maximum. Timestamp strings are Backend UTC `YYYY-MM-DDTHH:mm:ss.sssZ`, validated as real instants; input cannot set them. They are display metadata, not the concurrency authority.

`PersonaSet` contains `items` (0–5 `PersonaView`), `stateRevision`, and `activePersonaId` only when Active exists. The pointer must name an item in the same snapshot. Sort items by `createdAt` ascending, then ordinal `personaId` ascending. Return the complete bounded set without a cursor; do not add a general pagination exemption. Single-object reads also return the same transaction's owner revision.

| Operation | Exact request candidate | Success candidate |
| --- | --- | --- |
| `GET /v1/me/personas` | No query parameters or body | `200 {personas: PersonaSet}` |
| `GET /v1/me/personas/{personaId}` | Valid path ID; no query or body | `200 {persona: PersonaView, stateRevision}` |
| `POST /v1/me/personas` | `Idempotency-Key` plus `{displayName,tone,responseLength,formatStyle,expectedStateRevision}` | `201 {persona: PersonaView,stateRevision}` for first commit; identical current result with 200 for the P03 replay case |
| `PUT /v1/me/personas/{personaId}` | `{displayName,tone,responseLength,formatStyle,expectedRevision,expectedStateRevision}` | `200 {persona: PersonaView,stateRevision}` |
| `PUT /v1/me/persona-selection` | `{personaId,expectedRevision,expectedStateRevision}`; `personaId` is exactly 64 lowercase hexadecimal characters, without conversion | `200 {personas: PersonaSet}`; no null/empty selection or deactivation operation |
| `DELETE /v1/me/personas/{personaId}` | Required JSON `{expectedRevision,expectedStateRevision}` | 204 with no body; client independently rereads the set |

All JSON request objects are exact; query parameters are disallowed. Mutation JSON bodies have a proposed 4096-byte UTF-8 limit. Persona-scoped malformed JSON/shape, unexpected fields, invalid path format or oversized body maps to `REQUEST_INVALID` 400, with no raw parser details; this requests a scoped Transport error mapping, not a change to other routes. Correctly typed but invalid name/enum/revision values map to `PERSONA_INVALID` 422. POST requires one lowercase UUID v4 key in canonical hyphenated form; missing/malformed key maps to the existing `IDEMPOTENCY_KEY_INVALID` 400. Do not change other endpoints' key syntax. Keys on other Persona methods are rejected as `REQUEST_INVALID`, rather than suggesting replay support.

For activation, the body `personaId` is a transport identifier: require a string of exactly 64 ASCII characters, each `0`–`9` or `a`–`f`. Missing, null, wrong-type or malformed values all return `REQUEST_INVALID` 400, including a correctly typed string such as `not-an-id`, uppercase hex, whitespace-wrapped IDs or a non-64 length. Do not trim, lowercase, coerce or otherwise repair an ID. Authenticate first, then reject these inputs before the binding/account/Persona transaction. A syntactically valid ID absent from the authenticated owner's partition returns `PERSONA_UNAVAILABLE` 404 only after the usual authority and integrity checks; do not probe a foreign partition or treat malformed input as target absence. A valid live target then follows the existing revision checks. Transport, OpenAPI and PC02 must use this same candidate mapping; it remains subject to P01 approval.

Reuse the existing envelope `{error:{code,message,requestId}}` and unchanged `AUTH_REQUIRED` 401, `AUTH_FORBIDDEN` 403, `ONBOARDING_REQUIRED` 409 and `SERVICE_UNAVAILABLE` 503 semantics. New scoped candidates:

| Code | HTTP | Safe message |
| --- | --- | --- |
| `PERSONA_INVALID` | 422 | Use a name of 1–50 characters, valid style options and valid versions. |
| `PERSONA_UNAVAILABLE` | 404 | This Persona is unavailable. |
| `PERSONA_LIMIT_REACHED` | 409 | You can save up to 5 Personas. Delete one before creating another. |
| `PERSONA_COMMAND_CONFLICT` | 409 | This create request conflicts with an earlier operation. Reload before continuing. |
| `PERSONA_REVISION_PRECONDITION_FAILED` | 412 | Your Personas changed. Reload them before trying again. |

Error ordering: authenticate first; validate the route's bounded shape/key/domain values; then in a transaction resolve and validate binding/account before any Persona access. Missing binding gives the existing onboarding outcome; broken binding/account state fails closed. Read and validate owner state, live set and any addressed/derived candidate not already in that set next, including the orphan check. For create, apply the replay/stale decision below before fresh-create overflow/capacity checks. For other methods, target absence gives the generic 404 (or repeat-delete 204), then compare required revisions, then decide a no-op or effective mutation. No-op cannot bypass a stale precondition. Missing/non-owner IDs receive the same outcome without looking in another owner's partition. Invalid stored authority is 503, never a fabricated empty set or zero Active.

## P02 candidate persistence and atomic behavior

| Path | Exact record candidate |
| --- | --- |
| `accounts/{accountId}/persona_state/current` | `{livePersonaIds: string[], stateRevision: integer, activePersonaId?: string}`; unique IDs, maximum five, stored in ordinal ID order |
| `accounts/{accountId}/personas/{personaId}` | `{displayName,tone,responseLength,formatStyle,createdAt,updatedAt,revision}`; no owner/ID copy, per-item Active flag, prompt or historical snapshot |

No Account document field, receipt collection, query index, counter history, migration, TTL or scheduled cleanup is added. The synthetic fixture explicitly initializes the state as `{livePersonaIds:[],stateRevision:0}` for each isolated completed owner before use. Request paths never initialize, reset or repair a missing state. Missing/invalid state is 503. A nonempty membership with a missing/invalid member or invalid Active pointer is 503; an encountered live document outside membership is also corruption, not a record to expose or overwrite.

Keep the owner-state document after the last Persona is deleted. Its revision never decreases or resets while that Account remains in this scope; it contains no deleted ID, name, style or key. The existing account-lifecycle contract does not authorize recycling the same Account partition or resetting Persona state. Production provisioning, account deletion/recreation and migration remain a separate approval. A structurally valid out-of-band rollback is not detectable from these records and could reopen an old command; this candidate does not claim rollback protection. The isolated runner must stop clients/transports, settle outstanding requests and tear down the old session before cleanup, and use fresh Account partitions for a new run rather than reset a still-addressable owner.

Every route obtains one Firestore transaction snapshot: Auth Binding, Account, owner state, and each member referenced by that state. Read single/unknown targets only under that owner, using an extra point read when not already in the set. Validate all reads before writing. A whole-set read uses at most eight document gets per transaction attempt; a target/candidate lookup can bring the ceiling to nine. This is the proposed logical bound, not measured billing or an SDK-retry bound. No collection scan or composite index is required. Test actual reads and retries; do not invent a new outer retry loop.

| Operation | Atomic transition after valid authority/preconditions |
| --- | --- |
| Fresh create | Create live row at revision 1; set both timestamps from the Backend clock for the successful attempt; add membership and advance owner state by one; retain any existing Active pointer, so the new Persona is inactive |
| Edit | Require target and owner revisions. A changed normalized input replaces only the four fields, advances target and owner revisions once, updates only `updatedAt`, preserves `createdAt`, membership and Active |
| Activate | Require live target and both revisions. If different from Active, replace the pointer and advance owner state once. Target content/revision/timestamps do not change |
| Delete live target | Require both revisions. Remove live row and membership, clear Active only when it names this target, and advance owner state once. No other Persona is selected |
| Same-value edit or already-Active confirmation | After revision checks, return the current success representation with no timestamp/version/write change |
| Repeat delete of an absent own-partition target | After current account/state validation and confirming no orphan row exists, return 204 with no change even if the supplied versions are old; this reveals no previous ownership and never deletes another target |

Effective writes at maximum owner revision, or edits at maximum target revision, return 503 without partial writes. Reads, valid no-ops and the exact last-create replay may still succeed. Never wrap, reset or silently convert a failed write into a no-op. Full-set responses pair items, pointer and state revision from one snapshot; simultaneous create/delete/activation must either produce a coherent result or a safe failure. Do not infer that a response remains fresh after its transaction.

## P03 candidate creation recovery without receipts

The command identity is the complete tuple `(authenticated accountId, expectedStateRevision, Idempotency-Key)`, not the key alone across all versions. Changing the expected revision creates a different command; the client must not do that automatically to recover a failed/uncertain request. A deliberately new creation uses a new UUID key and a freshly read revision.

The server computes the candidate live ID using existing Node crypto capability, without a new package or secret:

```text
personaId = lowercaseHex(SHA256(UTF8(JSON.stringify([
  "persona_create_v1", accountId, expectedStateRevision, canonicalKey
]))))
```

Use all 256 bits. The canonical key is the validated lowercase UUID v4, not a user name or content-derived value. This ID is not authorization. Do not store or log the raw key, a separate key digest, the normalized request, a content fingerprint or a committed response copy. The only enduring content is the live Persona itself; deletion removes its ID from state and deletes the row.

After the common checks, let `S` be the supplied expected owner revision and `R` the current revision. Before any branch, point-read the derived candidate if it was not already read as a member. A present candidate outside membership is 503 even at full capacity or with stale input. All branches use this same validated transaction snapshot:

1. When `S` is below the safe-integer maximum and `R == S + 1`, check for the derived ID in the validated live set. If absent, return 412: another operation may have advanced the state. If present, it must be a valid revision-1 Persona; otherwise return 503 for inconsistent state. Compare all four normalized editable fields. Equal fields return 200 with that still-live view and current revision, with no writes; different fields return 409 `PERSONA_COMMAND_CONFLICT`.
2. If the exact replay branch did not apply and `R != S`, return 412. This includes older or farther-advanced state and a caller-supplied future version. Do not recreate an absent target, return deleted content or convert the request into a fresh create.
3. For `R == S`, fail closed on owner-revision overflow, then reject full capacity with 409. The derived candidate must be absent: an unexpected existing member/collision also fails 503 without overwriting it. Otherwise commit live row and owner-state increment together and return 201. No partial entity/receipt/proof step exists.

Replay must precede capacity so a lost response for the fifth Persona remains recoverable. With common authority/integrity checks passing, concurrent identical commands yield one 201 and subsequent 200 results only while no intervening effective owner mutation closes the window before each duplicate transaction is evaluated. An intervening effective mutation instead makes that duplicate return 412. Different keys at the same expected revision yield at most one commit; the loser receives 412. While the replay window is open, the same tuple with different canonical fields returns 409 `PERSONA_COMMAND_CONFLICT`, never an overwrite.

The replay window is **state-conditioned, not time-based**. It remains open only while that creation is the latest effective owner mutation and its live record remains unchanged. Any later effective edit, activation, deletion or second create advances the state and closes it. An old command is rejected even after the first Persona has been deleted and capacity is free. A same-value no-op does not close the window. No 24-hour validity or receipt-cleanup promise is introduced; no deleted content is retained to support recovery.

If a transaction never commits, an identical retry can still create at the original revision. If commit succeeds but the response is lost, replay can recover while the window is open. If another mutation happens first, the same retry safely returns 412 even when the original Persona still exists: this is the explicit usability cost of avoiding receipts. The UI must describe the original outcome as unresolved and reload current state; duplicate names and list absence cannot establish whether that earlier attempt succeeded. It must never silently use a new revision/key to create again.

The following summary assumes common authentication, account and stored-data integrity checks pass; it does not bypass their failure ordering.

| Validated transaction state | Required outcome |
| --- | --- |
| Creation committed; replay window open; same command tuple and normalized input | 200 with no write |
| Replay window open; same command tuple but different normalized input | 409 `PERSONA_COMMAND_CONFLICT` |
| Any subsequent effective owner mutation after that creation | 412 for the old create command, with no recreation |
| Only valid no-ops after creation, including same-value edit or already-Active confirmation | No owner revision change; window stays open; equal-input replay remains 200 |
| DELETE target already absent from the own-partition live set and no orphan row exists | 204 after account/state validation, including with old supplied revisions; this is the explicit repeat-delete exception |

### Client command recovery when a client scope is approved

Distinguish three states: an **HTTP attempt** records one request/response or transport failure; a **session command** records the outcome of the unchanged create identity and input across its attempts; a **page view** records a route's current rendering and operation generation. A known HTTP status is not automatically a known command outcome. These client rules belong to P08 or a separately approved client task; Backend-only delivery implements and tests the server contract above without Flutter changes.

Keep at most one pending create command in authenticated-session memory across Persona routes. Retain the original tuple and normalized input, with a session-instance identifier and a local command identifier that remain stable across retries. Do not persist its body/key in local storage, a durable queue or telemetry. Every response first checks the authenticated session instance, owner and command identifiers. If they still match the retained command, the session handler may settle its outcome even after the originating page was disposed or its view generation changed. Page disposal invalidates only that page's view updates; it neither cancels server work nor discards this session handler. A changed session/owner or an explicitly ended/replaced command rejects the old response, which cannot overwrite a new command.

| Event for the matching session command | Command outcome and permitted action |
| --- | --- |
| Timeout after dispatch or when dispatch cannot be ruled out, connection interruption, malformed success or another ambiguous transport outcome | Outcome uncertain; retain the exact original command, input, key and expected revision. Do not rotate them automatically |
| Wait budget expires before HTTP dispatch, with proof that this attempt was never sent | Mark this attempt not dispatched and prevent a late token result from sending it. This can settle command non-application only if no earlier attempt remains in flight or unresolved |
| Valid 200/201 with the approved create schema from any issued attempt | Confirm success and clear the retained retry envelope. Trigger an independent current-state read; page disposal does not prevent settlement. Success proves that command committed, not that its returned Persona is still current |
| Recovery of an uncertain command returns 412 | Mark recovery closed with original outcome still unknown; disable further retries of this command. Reload current Personas; this HTTP rejection does not prove the first attempt failed and does not clear the command as a definite failure |
| A matching late valid 200/201 arrives after recovery closed, before explicit command disposition | Confirm success from that proof. Do not reopen retry or replace shared state with the old success payload |
| User has reviewed a successful current-set read accepted under P08's revision rule and explicitly ends the unresolved command | Clear its retained envelope with an unresolved-outcome disposition, not a failure claim. Only then allow a deliberate new creation with a new key and a freshly read expected revision; list absence or a matching name is not proof of the old outcome |
| Validated rejection proves no commit under the server contract, with no other attempt in flight or unresolved | Command is definitively not applied and its retry envelope can be cleared. A response from one attempt cannot establish this while another attempt remains unresolved |

"Clear after a definite result" therefore means command-level confirmed success or proven non-application, not merely receipt of an HTTP response. Once success is confirmed, delayed errors, timeouts or 412s cannot downgrade it or recreate a pending command. An unresolved command may also end by the explicit reconciliation/disposition above, signout or identity change; these are not proof of server failure. App/process restart loses the in-memory command, so automatic recovery across restart is not promised. On a new session, reread current Personas and require a deliberate new create action. Editing pending input requires that same explicit reconciliation and disposition before starting a new intent; it cannot mutate an in-flight retry.
