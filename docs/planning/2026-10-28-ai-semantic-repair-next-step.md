## Trace of the goal/label issue

1. The [plan form](../../lib/features/ai_conversation/presentation/ai_plan_draft_page.dart#L59) places the user's entire trimmed goal field after `What I want to work on:` and the optional limits after a second natural-language heading. It does not add the synthetic test labels, and it has no structured field saying which part of the goal is context versus the desired task. The user can edit the whole resulting message before it becomes an unsent chat draft ([review and apply](../../lib/features/ai_conversation/presentation/ai_plan_draft_page.dart#L208); [chat handoff](../../lib/features/ai_conversation/presentation/ai_conversation_page.dart#L383)). Thus text entered as a label and text entered as a genuine test can occur under the same heading. That structure can leave interpretation ambiguous; the evidence does not establish that the heading caused the misreading.
2. In [fixed cases 1–4](../../tool/ai-companion-eval/fixtures/preserved-small-plan-cases.json#L4), the first two contain an explicit request for a quiet break alongside device-verification/record text; case 3 explicitly corrects the earlier interpretation, whereas case 4 really asks for a software test. The exact fixed rubric remains authoritative for comparison. A keyword rule that discards test-related text would wrongly discard case 4, and a blanket instruction to treat all text under the goal heading as a task would misread cases 1–2. In particular, case 1 does not expressly say the verification phrase is only a label until the later correction in case 3; it is not a separately typed field.
3. The production [serializer](../../backend/src/ai-runtime/infrastructure/local-chat-transport.ts#L65) appends the existing system instruction, optional Persona, history pairs and `currentMessage` without splitting or reclassifying the user message. Offline comparison of all 48 saved Groq request intents confirmed their recorded request hashes, and all 24 user/history message arrays in each profile match the captured golden inputs exactly; the baseline system matches the golden system in 24/24, while goal-v2 deliberately replaces it in 24/24. For cases 1 and 2, the captured input has eight actual LF characters and zero literal backslash-`n` pairs. This rules out loss or newline escaping **at the captured serializer/request boundary** for these cases; it does not prove a physical-device send path.
4. The current production system prompt asks the model to use the conversation and not invent facts, but does not itself encode a label-versus-goal rule. The [local prompt candidate](../evidence/2026-10-28-li-ai-repair/prompt-v1.patch) and [goal-v2](../../tool/ai-companion-eval/goal-prompt-candidate.mjs#L3) both expressly ask it to distinguish labels and actual tasks; cases 1 and 2 still fail. The observed failure is therefore model instruction-following/interpretation under the supplied text, with an input-structure ambiguity; it is not proof of a deterministic serializer defect, nor proof that the baseline system instruction alone caused the issue.

The chat's current [candidate gate](../../backend/src/ai-runtime/infrastructure/local-chat-transport.ts#L82) checks the output shape and non-empty text; it does not prove natural-language relevance, exact durations or grounded materials. That matches its stated scope and is a limitation, not evidence of a broken JSON parser. The distinct, more restrictive semantic policy is not a drop-in correction: changing active gates could reject legitimate chat or code and needs its own approved scope.

## Literal `\n` in two candidate replies

In goal-v2 cases 1 and 4, the saved provider assistant content is itself an inner JSON document whose relevant bytes are backslash, backslash, `n` (92, 92, 110). Decoding that document once yields a message with backslash, `n` (92, 110), not a line feed: three pairs in case 1 and nine in case 4. Both messages have zero actual LF characters. In this 24-response run these are the only two such messages; the Groq baseline has none. The evaluator saves `message.content` after decoding the provider envelope ([adapter](../../tool/ai-companion-eval/groq-evaluation.mjs#L225)), so the earliest retained boundary is the provider's assistant content; the evidence does not distinguish model generation from an upstream provider transformation.

The production [parser](../../backend/src/ai-runtime/domain/parse-output.ts#L35) performs one JSON string decode, and the normal [message renderer](../../lib/features/ai_conversation/presentation/ai_conversation_page.dart#L2438) passes available text to Flutter `Text`. A local, no-network parser probe preserved a real LF and a literal backslash-`n` in code as two distinct valid strings. The probe used the ambient Node 26.12.1 and is a diagnostic observation, not a pinned-runtime acceptance test. This is correct decoding for the received JSON; neither the parser nor the renderer introduced the two characters. If that candidate text reached this renderer unchanged, the characters would be visible, but Groq is not integrated and no device observation is claimed. The current schema allows such literal text, so this is an observed candidate output/presentation defect, not a proven application escaping bug.

Do not globally replace backslash-`n` with a newline: the literal sequence is valid in code and in a user's requested exact text. Nor should a presentation fix silently rewrite stored messages. If a future approved design needs to normalize provider output, it must first define a trustworthy context or explicit user-controlled, reversible display behavior; an ordinary plain-text message alone does not distinguish intended code from an accidental escape.

## Single-variable experiment: original proposal and execution update

**Subsequent execution update:** LI later granted this specific pass in
`d811c23`. It completed 24 calls on 28 October; the
[baseline-medium assessment](../evidence/2026-10-28-li-ai-repair/groq-baseline-medium-assessment.md)
records 16 passes and eight failures, with six original failures improved,
four remaining and four regressions. The candidate is rejected. The proposal
below preserves what was reviewed before execution; it is no longer a pending
or reusable grant, and it does not establish a production model selection.

**Hypothesis:** with the original production-prompt messages and the same Groq model and output ceiling, selecting `reasoning_effort: "medium"` instead of `"low"` may improve some goal, constraint, and historical-context failures. A negative or mixed outcome is useful evidence too. This asks whether that provider setting is worth investigating; it does not assume or prove the model's hidden reasoning process or a particular amount of additional reasoning.

The parent agent checked Groq's official [reasoning documentation](https://console.groq.com/docs/reasoning) and [API reference](https://console.groq.com/docs/api-reference) on 28 October: GPT-OSS 120B documents `low`, `medium`, and `high`, with `medium` as the default. This is documentation evidence, not proof that a future account request will be accepted, free, or produce better answers. Recheck the model, plan, limits and Free eligibility immediately before any separately authorized run.

Use the retained **Groq baseline** as the comparison, not goal-v2. For each of the same ordered 24 saved baseline request bodies, change the JSON value of `reasoning_effort` from `low` to `medium` and keep every other request property identical: `openai/gpt-oss-120b`, all production system/Persona/user/history messages, strict `ai_assistant_message_v1` schema, `max_completion_tokens: 2048`, `include_reasoning: false`, and `stream: false`. Do not add a seed, sampling parameter, tools, new output schema, special case, or hidden prompt. Before dispatch, an offline comparison must assert that this is the only request-body difference and retain both original and candidate hashes. The isolated `baseline-medium` adapter profile and its runner policy are now prepared, but no live call is authorized or executed. The combined adapter, authorization/pacing and golden-request tests passed 38/38 on pinned Node 24.19.0; all 24 candidate request bodies differ from baseline only in this value. Both earlier profiles also retain byte-identical requests against their saved intents. No production transport or user data is involved.

If LI separately authorizes at most 24 new synthetic Free-plan calls, execute one serial call per unchanged fixture, preserving a fresh private run directory, exact requests/responses and the existing physical-receipt, 45-second delivery and 120-second receive boundaries. No automatic retry, fallback, replay of unknown results, paid upgrade, or silent resumption. Stop on 429, refusal, truncation, invalid/late output, missing required usage or an unconfirmed outcome. Starts should be at least 61 seconds apart; an offline calculation of the 24 candidate bodies gives a maximum 4,390 under the conservative `whole request UTF-8 bytes + 2,048 completion + 512 wrapper` heuristic, below the previously observed 8,000 TPM for a single isolated request. This heuristic is not a tokenizer, rate-limit guarantee or cost guarantee; account sharing, provider limits and rate windows may differ. The longer spacing is an operational safety difference, so do not compare latency or throughput.

Review each terminal response against the **unchanged 24-case rubric**, including the original ten failures and original passes. Report case-level improvements, remaining failures, regressions, invalid/late outputs and available usage; do not reinterpret valid JSON as a semantic pass. A candidate for full semantic acceptance requires all original failures corrected with no regression among the original passes, plus the existing independent review and later runtime/device gates. One run per case is exploratory: nondeterministic sampling, provider/model revision and time can affect outputs, so an observed change cannot establish causality or a reliability rate. Any mixed/failed result remains unadopted; do not turn it into another prompt sweep.

The existing offline probes already establish the examined text boundaries. Add targeted regression coverage only if a later change actually touches those boundaries; copying the present implementation into new tests is not the next repair. A new UI field, structured focus quotation or intermediate plan schema could be explored separately if this experiment fails, but would introduce additional variables and product/architecture decisions; none is necessary for this single-variable comparison. Provider adoption and processing of real private data remain subject to the existing consent and deployment decisions.
