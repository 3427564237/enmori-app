## Notification renewal and timezone evidence

- The backend accepts an explicit registration lease of at most 30 days. `replaceRegistration` derives expiry from the current registration request; status reads and dispatch do not renew it. The existing regression covers expiry, explicit renewal and unchanged expiry after dispatch: [store](../../backend/src/proactive/infrastructure/firestore-first-flow-store.ts), [test](../../backend/test/proactive/firestore-first-flow-store.test.ts). The source limit is not a new readback of the live configured duration.
- The app exposes **Check notification status** and **Enable system notifications**; the latter explicitly re-registers after fresh consent/settings/permission checks. Token rotation may replace an already-current registration, but rejects expired or different-installation registration. Ordinary use and delivery therefore cannot be relied on for automatic monthly renewal. See [controller](../../lib/features/proactive/proactive_notification_controller.dart) and [registration model](../../lib/features/proactive/domain/proactive_messaging.dart).
- The API/model supplies `expiresAt`, but [Push controls](../../lib/features/proactive/presentation/proactive_push_controls.dart) currently displays only active/expired status, not the actual expiry date. This leaves the operating plan's “show expiry” outcome open. Until that is closed, the handoff must not imply a visible countdown or automatic two-month registration. For a full 30-day initial lease, two further explicit registrations are needed to span 61 days if no authorized token refresh renews it. Use each actual expiry, not an assumed calendar month; registration on another installation replaces the former one. Notification permission/channel and delivery remain separate from canonical in-app follow-up availability.
- Android resolves the selected civil time with `ZoneId.getRules().getValidOffsets`: skipped times return no candidate and repeated times return both candidates for confirmation. The native channel refuses this operation below Android API 26; it does not invent a local-time conversion. Settings displays the confirmed IANA zone and quiet hours. Source: [native resolver](../../android/app/src/main/java/com/enmori/app/FollowUpCivilTimeResolver.java), [channel](../../android/app/src/main/kotlin/com/enmori/app/MainActivity.kt), [settings page](../../lib/features/proactive/presentation/proactive_settings_page.dart).
- The existing dependency-free [native resolver check](../../android/app/src/test/java/com/enmori/app/FollowUpCivilTimeResolverCheck.java) was compiled and run in this audit: **PASS**, including Singapore, New York gap/fold, Australia/Lord_Howe half-hour fold, a skipped date, UTC and invalid input. This is JVM source evidence, not an Android device timezone-database check. [Backend policy tests](../../backend/test/proactive/policy.test.ts) separately cover Singapore quiet-hour boundaries, travel to another zone and DST; this audit inspected but did not rerun those tests.

Singapore/Australia delivery must use the teacher's actual confirmed IANA zone, not a country-wide offset assumption. Exact teacher city, Android version, phone/notification behavior and networks remain unverified. Existing resolver examples do not establish cross-country physical delivery or iOS compatibility.
