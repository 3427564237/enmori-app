It needs no real provider, Activity adapter, new Account population, general search framework, new index or stored search/name copy. The capability authority is Q18-A's explicit established-friend name search, together with Q04-D/M13 and the existing Profile and F01–F05 privacy boundaries. LI must confirm the following concrete delta and persist that decision under `docs/decisions/`; SHI then reviews any new JIN implementation at its actual head. Existing approvals need no repetition.

| Decision | Recommended candidate for LI confirmation | Alternative or retained limit |
| --- | --- | --- |
| FS01 scope and matching | Search actual DisplayName only among freshly authorized established friends. For query and comparison key: validate well-formed Unicode and reject Cc/Cf/Zl/Zp characters before trimming; ECMAScript `trim()`, NFC, locale-independent `toLowerCase()`, then NFC. Require 1–50 Unicode scalars after normalization for the query; use substring matching against the normalized key of the already-valid stored DisplayName. Keep the original approved display value in the response; never rewrite storage. | Prefix rather than substring is a bounded alternative requiring LI selection. No locale collation, accent stripping, transliteration, fuzzy matching, full Unicode case folding or Username fallback. Thus `ALICE`/`alice` match; composed/decomposed accents match; `Jose` does not match `José`, and `SS` does not match `ß`. This is not Q18 Add Friend canonicalization. |
| FS02 operation and cursor | Propose `GET /v1/me/friends/search?q=...&cursor=...`; required single `q`, optional single `cursor`, no unknown parameters, AccountId or caller page size. Return the existing `{friends:[{username,displayName}],nextCursor:string|null}` shape, purpose-limited to search. Cursor candidate is canonical unpadded base64url UTF-8 JSON with exact ordered keys `{v:1,q:<normalized query>,after:<canonical UUID-v4 entryRef>}`; maximum 512 ASCII cursor characters, strict decoding/re-encoding and exact field/type validation. Require cursor query equality and current existence of its entry within the authenticated owner's initialized index. | Reusing a bare list cursor without query binding is not proposed. The cursor is an untrusted continuation, not an authorization credential; owner/pair/presentation checks remain mandatory. No server-held search session, total count, opaque Account ID or private record identity is returned. No new crypto/dependency is needed for this proposed cursor. |
| FS03 reads and privacy | Reuse feature-local owner pointers: one transaction, at most 20 scanned rows plus one lookahead, full current owner/pair/target/name/reservation checks before name matching; no target expansion for lookahead, scan-to-fill, global Account query or read-time writes. Continue after the last scanned entry even when zero matches are visible. Proposed maximum remains 106 document gets per transaction attempt; actual implementation must measure it and report SDK retries separately. | Known valid privacy/eligibility denial omits; missing/malformed authority fails the page even if the query would not match. Each page is a fresh read; no frozen search snapshot or completeness promise across concurrent changes. Reuse approved index/fixture lifecycle; no real population/backfill/retention approval. |
| FS04 safe errors and validation | Reuse authenticated requester/onboarding/eligibility guard before target evaluation, existing generic errors, `REQUEST_INVALID` 400 for invalid query/cursor and `SERVICE_UNAVAILABLE` 503 for malformed/unavailable authority. Validate inputs after requester authority and before scanning targets. Privacy-preserving omissions expose no reason/count; queries and cursor values never enter logs. | No search permission is inferred from exact-lookup's minimal identity exception. No new public target existence/error category or operational threshold is selected. Real-use abuse protection remains part of the real-account gate. |
| FS05 UI and acceptance | Add explicit Search and Clear controls to the existing isolated `/friends/list`. Submit on Search; blank client input prompts validation, Clear reloads the ordinary unsearched first page. Changing/submitting query resets page/cursor and invalidates old in-flight results; account/session changes clear query and rows. Next replaces the current page; Reload restarts the current query. Rows remain non-actionable. Candidate empty copy: `No matching friends on this page.`; show Next when continuation exists and never report a complete empty friendship set from a filtered page. | No filter of only the currently loaded page. No new Profile link, Home route, Activity, Special Care, notification or unfriend. Final UI/copy and client non-AI budget remain subject to this exact scope approval; shared Home/router redesign is unnecessary. |

The 512-character bound accommodates the normalized 50-scalar query and fixed version/UUID structure; invalid or noncanonical encodings are rejected, not coerced. Modifying a cursor cannot grant another owner's access or suppress reauthorization. A client can deliberately restart/skip its own authorized range; this cursor does not promise an immutable result set. No query or display-name copy is persisted server-side.
