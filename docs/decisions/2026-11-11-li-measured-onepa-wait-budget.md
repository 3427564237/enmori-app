# Measured onePA wait budget within LI's approved demo recovery

Date: 11 November 2026 (Asia/Singapore). Scope: implementation values selected under LI's existing instruction “响应时间长就限制时间加长一些” and subsequent request to repair onePA. This records the measured refinement; it does not attribute these specific numbers to a new user quote or create a new performance requirement.

The [immediate demo decision](2026-11-11-li-immediate-demo.md) first selected source 90 seconds, aggregate 110 seconds and relevant clients 120 seconds. The original Azure reader then demonstrated that a duplicate page-zero response was misclassified as page one. Its repaired pagination reached genuine offsets 0, 10 and 20, with approximately 24, 20 and 19 seconds waiting for those pages, before the 90-second caller deadline interrupted the next page. Source identity, parser and ordinary anonymous access are retained; there was no challenge/403/429 in that observation. Three pages do not satisfy the approved five-page bound.

Refine only these existing slow Event-dependent budgets: **180 seconds per provider batch and onePA catalogue read; 210 seconds for the multi-provider recommendation/social snapshot; 225 seconds for Event browse/recommendations, friend discovery, and All/Event Friend Activity reads**. Retain the legacy single-provider 10-second snapshot and ordinary 15-second operations, including Check-in-only Friend Activity. Existing AI deadlines, mutations, account consent, source validation, provider coverage limits, caches, retry policy and unknown-result behavior are unchanged.

This explicitly supersedes the earlier selected 90/110/120 values only for those paths. The 225-second client bound remains below the current documented [Azure Linux approximately 240-second request limit](https://learn.microsoft.com/en-us/troubleshoot/azure/app-service/web-request-times-out-app-service). It is not a platform setting change, new background service, source permission, partial-success waiver or claim that the original 15-second performance target is met.

Repair and independently review page correlation/cancellation first. Then verify one bounded candidate read on the existing Azure host, including all five page identities and cleanup. If the complete source still fails, preserve its unavailable result and report the remaining measured bottleneck; the new time budget alone is not acceptance.
