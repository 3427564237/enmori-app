## 5. Deterministic backend finding: expired projection rejects fresh stable detail

**Source-local defect established; attribution of any particular production failure remains unproven.** In `ControlledSourceProjection.event`, the stable-ID path captures the current snapshot, makes an exact underlying source lookup after a cache miss, then calls `requireCurrent(epoch, cached, signal)`. `requireCurrent` rejects when `cached` is no longer live, even if it was already expired before the new lookup and the underlying source has just succeeded. Unlike `firstBatch`, this path does not first retire that expired snapshot.

Relevant implementation: `backend/src/event-browse/infrastructure/controlled-source-projection.ts`, stable `event` path around lines 113–130, `live` around 235, `requireCurrent` around 246, `firstBatch` around 250. Actual provider `event` methods perform exact source resolution; they do not require the caller to open Browse first. The combined source delegates to the ID's provider.

| Cached snapshot is 299,999 ms old, exact lookup succeeds | Stable detail succeeds with the fresh detail, not the list summary. |
| Cached snapshot reaches exactly 300,000 ms; same stable ID read twice | Both underlying exact source calls resolve successfully, but both projection calls reject with `dependencyUnavailable`. No external service or race is involved. |
| Refresh `firstBatch`, then read the exact same stable ID | Stable detail succeeds again. This is a local same-ID recovery; it is not a production recovery claim. |
| Snapshot expires during the exact lookup | Current implementation rejects; do not silently relax this existing in-flight freshness boundary. |
| A new page-zero generation publishes while a raw detail read waits | Old in-flight result is correctly rejected; replacement fencing must remain. |

**Smallest proposed backend repair, requiring approval before implementation/deployment:** after joining and validating any pending replacement, but before starting a new exact stable lookup, atomically retire an already-expired cached snapshot, clear its observed-page/read state, and advance/capture the new empty generation. Then run the existing exact provider lookup and keep the final epoch/snapshot/pending/abort fences. This creates no cache snapshot and does not re-date old data: the exact provider read must satisfy its own current-source rules. When an originally live snapshot was captured, that snapshot remains the in-flight freshness bound; when an expired snapshot was retired before admission, there is no old snapshot to bind the new exact read. These are distinct admission states, not an exception that releases already-admitted stale work. No full-catalogue refresh is needed solely to unblock a fresh exact lookup. Do not remove `requireCurrent`, reuse expired data, extend TTL, return a list summary as full detail, auto-retry, change provider access or increase timeout budgets. Keep the existing fail-closed behavior for replacement admitted during the lookup and for a snapshot that was live at admission but expires while waiting; broaden that boundary only with separate contract review.

Before a repair is accepted, turn the temporary observation into permanent failing-before/passing-after regression coverage. Include both provider identities; cold/live/expired snapshot states; two repeated reads; same-ID recovery; failed/pending refresh; abort/disable; expiry during the lookup; source failure/undefined; and concurrent generation replacement. Re-run the existing source-freshness and generation tests plus backend verification. A subsequent same-backend production sequence must distinguish exact-detail success from `detailsStatus: unavailable` and verify recovery after more than five minutes without requiring a user to visit Browse first.
