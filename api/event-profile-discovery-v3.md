# Event, recommendation profile and friend discovery v3

Authority: [LI 28 October decision](../docs/decisions/2026-10-28-li-event-profile-discovery.md). Normative wire shapes are in [OpenAPI](openapi.json). Earlier v1/v2 and presentation contracts remain historical; see the decision for the narrow supersession scope.

## Identity and public content

Ticketmaster stable identifiers remain unchanged. onePA uses `pa_` browse IDs and `pa_event_` stable IDs derived from source identity, never title. Cards carry summary/decision metadata; detail may carry 30,000 characters and up to twelve named sections of 12,000 characters. Optional source fields do not change old required Event fields. Unavailable full-detail acquisition is different from a source supplying no description. Official details and booking links are distinct only when verified against the selected occurrence. Opening either does not mutate participation.

Per the [29 October PM decision](../docs/decisions/2026-10-29-li-event-overview-without-introduction.md), overview cards omit description excerpts and missing-description placeholders, including when cached text exists. Actual descriptions remain in the in-app detail. This changes presentation only; optional API description fields and demand-driven acquisition remain compatible.

The [17 November interest-discovery amendment](../docs/decisions/2026-11-17-li-interest-discovery-uiux.md) expands the earlier first-50-only onePA sample: retain the default five pages (at most 50 records) plus the first official search page for each of its 14 fixed public queries (at most 10 each), for at most 190 raw records before stable-identity deduplication. All users share the same manifest; no user interests are sent upstream. A short or empty valid first page completes that query. There are no extra search pages, alternative-keyword retries, courses or per-card detail reads. At most four ephemeral pages run concurrently (one default task and three search workers). Under the [17 November supplemental-query amendment](../docs/decisions/2026-11-17-li-supplemental-query-degradation.md), the required default group must complete, and each of the fourteen supplemental groups must settle as complete or failed within the unchanged shared 180-second budget. Only complete groups contribute rows; a failed supplemental group is not retried and does not discard other completed groups. A default-group failure, global deadline, external cancellation, supersession or conflicting normalized identity still invalidates the entire onePA acquisition. No in-flight prefix or stale failed-group data is published. Ticketmaster remains independent.

onePA continues to expose batches of at most 20, and combined batches at most 40 rows. Full detail is read on demand; publicly linked sitemap resolution remains a bounded fallback for saved identities. Plain public responses are used when complete, otherwise ordinary ephemeral Chromium renders the public page. Ticketmaster keeps its existing API batch limits. Five-minute memory reuse/coalescing and timeouts apply; no copied durable content library. This bounded sample is not a complete Singapore catalogue and does not guarantee events for every interest. Browser failures, access challenges and sign-in-only prices/vacancies are never converted to successful or free/available results. The exact onePA title mapping, accepted Published values and retained privacy filters are specified by the same amendment; Ticketmaster classification remains unchanged.

The [11 November measured-budget amendment](../docs/decisions/2026-11-11-li-measured-onepa-wait-budget.md) supersedes the earlier [5 November read budgets](../docs/decisions/2026-11-05-li-followup-runtime-admin-validation.md) for the affected paths: provider batch/onePA catalogue 180 seconds, multi-provider recommendation/social snapshot 210 seconds, and Event browse/recommendation plus applicable friend-read clients 225 seconds. Detail GETs retain their existing separate budget. Other reads, writes and the AI target are unchanged. When a provider fails on page zero, its unavailable status persists through that listing instead of restarting the failed acquisition for every healthy-provider page. A fresh page-zero read retries both sources.

## Private recommendation profile

`GET/PUT /v1/me/recommendation-profile` authenticates the current owner and returns `Cache-Control: no-store`. PUT replaces all nine preference fields and requires `expectedRevision`; GET returns those fields plus `revision`. A missing stored projection reads as revision zero, all grants off, null birthday/home area. Existing Profile privacy and free-text region remain untouched. The nested account projection is deleted with its account. No birthday, coordinates or raw matching fields are added to discovery cards, AI input or logs.

Dates are strict civil dates. Future birthdays are rejected. Age advances on 1 March for 29 February birthdays in non-leap years. Event eligibility uses the Singapore event date; friendship age uses the current Singapore date. Missing DOB does not assert eligibility. Only explicit source restrictions/target ages are usable; no title/category demographic inference.

Area catalogue: bundled URA MP2025, published 27 February 2026, 55 planning areas. Code lookup and point-in-polygon share that version. Device foreground geolocation requires user opt-in and OS permission, has a 15-second request limit and five-minute reuse. Accuracy above 250 metres or sampled accuracy-circle points crossing an area boundary is considered unresolved. Raw coordinates never cross the Backend API. Activity context precedence is session manual selection, valid device location, synced home area, Singapore-wide. Manual override is cleared only explicitly or on account/session replacement; automatic location does not modify home area.

Unknown save results/conflicts retain the local draft and require owner readback. Reload saved settings or explicitly keep the draft against the reread revision. New accounts get optional guidance after existing onboarding; existing accounts get a completion entry. Skipping does not enable discovery or fill missing values.

## Discovery and ranking

`GET /v1/users/{username}/discovery-card` returns only username/display name when current eligibility, discovery and processing consent permit access. Existing avatar authorization remains separate. It does not permit private full-profile access. Friendship actions use their existing current-state checks. Default discovery is off. Both parties must consent to each optional matching factor; authorizing matching does not publish the underlying field. Existing relationship, blocks, pending requests, ignored accounts and availability exclusions remain.

Event formula `event_recommendation_v3`: interests 4 each; visible friend involvement 2 each, max 10; same area 2, else same broad region 1; explicit target-age match 1. Explicitly age-ineligible and known closed/cancelled/sold-out events do not enter personalized recommendations but can still be browsed. Friend v3: interests 4; common authorized events 2; same area 2 else broad region 1; shared affiliation 1; age within five years 1 only after another qualifying factor. Stable tie order and reasons are retained. No unauthorized/missing factor earns points, and failed reads remain failures.

The [15 November Event ordering amendment](../docs/decisions/2026-11-15-li-event-interest-first-ordering.md) places all candidates with at least one current active selected-interest match before candidates with none. Within each group, use the existing score descending, start instant ascending and stable identity ascending. Rank the complete set before Home Top 2. Non-interest candidates remain eligible only through existing permitted positive signals. This also applies to the legacy v2 Event representation, retaining its weights and allowed reasons. Formula identifiers, reason receipts and Friend ordering are unchanged.

V3 Event recommendation responses may include `sourceStatus: [{provider, available}]`, limited to the distinct providers `ticketmaster` and `onepa` with boolean availability. It is captured and frozen with the complete candidate snapshot across its pages, reused only with that snapshot and retired on refresh/expiry. It is never read from mutable global provider status when returning a different request. Missing status or an omitted provider means unknown; a healthy source with no eligible activities remains available. Malformed present status is an invalid response. A previously healthy provider failing on a later page still invalidates the incomplete ranking snapshot; required personal-data, permission, paging and generation failures remain errors. Both providers failing remains unavailable, not a successful empty result. Status contains no private exclusion reason and no source activity payload.

The same amendment adds immutable coverage completeness, separately from availability. A valid onePA result with failed supplemental groups remains available, including when its admitted groups contain no eligible rows. V3 recommendations may emit top-level `sourceCoverage: [{provider:"onepa", complete:boolean}]`; their `sourceStatus` rows retain exactly `provider` and `available`. Browse retains its existing top-level keys and may instead add `coverageComplete:boolean` to its available onePA `sourceStatus` row. This representation difference preserves already delivered strict v3 clients. Known coverage is emitted only with explicitly available onePA data, frozen with its batch and complete candidate snapshot, retained through provider exhaustion and retired on refresh/expiry. Missing/empty coverage is unknown, never implicitly complete. Malformed, duplicate or contradictory coverage is invalid. A coverage change during traversal invalidates the generation; all available pages of the admitted source set must still complete before ranking. No activity payload, per-interest absence claim or private exclusion reason appears in coverage. New clients show incomplete-range messaging for empty and nonempty results, separately from whole-provider unavailability.

Only the v3 representation emits source status and coverage; v1/v2 omit both. Existing v3 readers remain compatible, and new clients accept its absence without inferring health. The [17 November decision](../docs/decisions/2026-11-17-li-interest-discovery-uiux.md) also replaces the affected Event empty copy/actions with current-range wording, Edit interests and Browse, and presents provider degradation independently for empty and nonempty results. It does not change recommendation eligibility.

Friend responses expose only the requesting user's `ownState`: disabled, incomplete, no_matches or ready. Home retains the top-two limit; all candidates remain accessible from Friends. Field/consent changes invalidate the affected client views and stale asynchronous responses. Cross-device changes are reread on entry/refresh; no realtime push system is introduced.

## Verification boundaries

Source tests, provider probes, running Backend, signed APK and physical-device/account UAT are separate. See the [v42 evidence record](../docs/evidence/2026-10-28-event-profile-discovery/verification.md); an APK or successful source request alone does not establish the complete registration-to-booking journey.

## Installed-client compatibility

New Flutter reads send `X-ENMORI-Contract-Version: 3` on Event browse/detail and Event/Friend recommendation requests. The header selects a representation, never identity or authorization. Without it, Event browsing keeps its existing Ticketmaster-only identifiers/scope and fields; provider failure remains an error. Event recommendations rerank the same currently authorized signals using v2 weights, with no onePA rows or v3 age/area reasons. Stable detail omits the added `content` object. Friend discovery continues to require the new opt-in/processing permissions, but old clients receive only public-profile-compatible candidates and existing reason forms, without `ownState`. No existing user is opted in by the compatibility path. Installing v42 is required for the complete new flow.
