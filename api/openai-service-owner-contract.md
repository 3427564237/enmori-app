# OpenAI same-service restart ownership

Authority: [LI's 11 November implementation approval](../docs/decisions/2026-11-11-li-teacher-stability-implementation.md), approving the [concrete restart proposal](../docs/planning/2026-11-11-openai-service-restart-proposal.md). This supersedes the 5 November prohibition on automatic takeover only for the configured existing Azure Japan service after a separately verified stop/drain migration. It does not authorize a second host, region, local worker, scale-out, automatic funding or a live migration by source implementation.

No public route, DTO, header, client choice or Admin action is added. The original manual `claim` branch remains supported. The private configuration accepts exactly one of `claim` or `ownership`; both, neither or malformed ownership close cloud admission and Settings writes. `ownership` contains exactly `mode: renewable_service_lease`, `serviceKey`, `leaseDurationMs: 120000`, `renewEveryMs: 30000`, `safetyMarginMs: 15000`. The opaque service key uses 1–64 ASCII letters, digits, underscore or hyphen. Configuration is copied and frozen; it cannot become another service identity during a process.

The existing `ai_runtime_fence/current` shape remains unchanged. The new Backend-only `ai_runtime_fence/service_owner` record contains exactly:

| Field | Contract |
| --- | --- |
| `schemaVersion` | `openai_service_owner_v1` |
| `serviceKey` | Exact configured opaque service identity |
| `enabled` | Operator-controlled boolean |
| `processEpoch`, `generation` | Same epoch as current runtime fence; generation is a positive safe integer |
| `leaseVersion` | Nonnegative safe integer; strictly increases on each lease write |
| `renewedAtMs`, `leaseUntilMs` | Trusted Firestore transaction observation and observation plus 120,000 ms |

The operator-installed initial vacant record has the captured fence, version 0, and both times 0. An explicitly reconciled later vacant record preserves its incremented version; both times are again 0. Startup never creates, repairs, clears, rebinds or enables either record. Missing, disabled, corrupt or identity/epoch-mismatched state stays ordinary-only with cloud unavailable. Exhausted integer ranges close admission.

Every acquire/renew transaction uses `maxAttempts: 1`. It reads the owner and fence before any write and consumes their immutable SDK `readTime` metadata projected by `getSnapshot`. It uses the earlier observation, floored to milliseconds, so discarded precision never fabricates a later expiry observation. No cached read, local wall time, client time or previous read-only snapshot proves remote expiry. Occupied observations stage no writes. Acquisition requires matching enabled service identity/epoch and server time at or after expiry; it advances the existing fence generation and owner epoch atomically while preserving `cleanupGeneration`. Renewal requires the exact original epoch, version and times with a still-unexpired server lease, and writes only owner lease metadata. A thrown/lost SDK ACK is unknown, even if its write actually committed.

`RenewableServiceOwner` records its local instant before submitting each operation. A definite ACK must arrive strictly before 15 seconds. The usable capability expires at original submission plus 105 seconds, never ACK time plus 105 seconds. Renewal cannot resurrect an expired, stopped, changed or retired original capability. All dispatch, token-count, publication, Settings and proactive guards share this capability in addition to the existing durable runtime fence and per-account consent checks. Cloud Conversation store/maintenance transactions also use the ownership-fenced gateway. Failed/unknown renewal retires synchronously; late callbacks cannot re-open it.

The Linux clock reads `/proc/uptime` synchronously, alongside existing monotonic and wall observations. It uses the greatest elapsed interval. Missing/malformed/backward observation or wall-versus-monotonic elapsed divergence greater than 1,000 ms permanently retires the clock. Even before timer callbacks run, a resumed process's next synchronous capability check observes suspend-inclusive expiry. This does not use local clocks to judge another server's lease. Unsupported platforms stay closed and require manual recovery.

Only a definite occupied result permits another fresh no-write observation in the same process. These observations are spaced by at most the existing 30-second renewal interval or remaining server lease, bounded by 135 seconds from composition start. At 135 seconds the process stops observing and remains ordinary-only, with AI unavailable and Settings writes closed. It does not restart just because a lease is occupied, keep polling forever, replace an unknown acquisition, or claim availability. An unknown acquisition never emits the active-owner-loss restart event.

After loss of a previously active owner, all local capabilities retire before the loss event. Azure begins the existing shutdown path, with a **15-second best-effort disposal deadline**, then exits nonzero whether shutdown completed or remained uncertain. This 15-second disposal bound is the coordinating agent's documented implementation choice within the approved process-disposal requirement, not a new quoted PM decision. The watcher is installed before runtime construction, covering loss during initial retirement/maintenance as well as after listening. Its timer/disposer are injected in tests and fire only once. Ordinary manual SIGTERM/SIGINT retains the previous drain behavior. No exit, abort, cancellation or timeout is reported as physical remote model/FCM settlement; durable monetary holds and uncertain occurrence states remain untouched.

The same owner is used by ordinary Conversation, Persona preview, proactive execution, source/publication guards and all Settings writers. A published occurrence with an in-flight FCM result remains dispatching until safe recovery classifies it unknown; neither restart nor a late old callback authorizes generation or sending again. There is no early graceful lease release: a new process waits for server expiry. Monetary recovery uses the separately approved deployment grant validator; acquiring or renewing ownership never refreshes a grant, balance, price, credit, quota or spend.

Source and isolated Emulator evidence are distinct from deployment, measured recovery time, two-month reliability and physical device acceptance. Live migration/rollback must follow the approved proposal's stop/drain, exact ledger preservation, vacant-record CAS and explicit re-arm requirements. Old binaries do not implement this capability and cannot participate in the initial transition. A manual epoch change intentionally leaves an owner mismatch until an operator performs the approved re-arm; deleting/resetting the owner record is not rollback.
